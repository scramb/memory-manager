# Kubernetes deployment (`deploy/`)

## What this is

`deploy/` is a generic Kustomize base for memory-manager: the
`Deployment`, `Service`, a public `HTTPRoute` (Gateway API), the CloudNativePG `Cluster` that
runs its Postgres+pgvector index, and the `ExternalSecret` that pulls everything the server must
not keep in Git (the vault deploy key, OIDC client secret, webhook secret, OAuth client-secret
encryption key) from an operator's own secret store.

It is deliberately **operator-agnostic** (`CLAUDE.md`: a public repository carries no real
hostnames, cluster names, secret-store paths, IPs or namespaces). No `namespace:` is set here -
every value an operator must supply is a clearly-named placeholder instead:

| Placeholder | Where | What it becomes |
|---|---|---|
| `memory.example.com` | `deployment.yaml` (`PUBLIC_URL`), `httproute.yaml` (`hostnames`) | the server's own public URL - both must match exactly (ADR-0004) |
| `idp.example.com` | `deployment.yaml` (`OIDC_ISSUER`) | the upstream OIDC provider |
| `you@example.com` | `deployment.yaml` (`OIDC_ALLOWED_EMAILS`) | the login allowlist (deny-by-default) |
| `git@git.example.com:memory-manager/vault.git` | `deployment.yaml` (`VAULT_REMOTE`) | the vault's own git remote |
| `gateway-name`/`gateway-namespace` | `httproute.yaml` (`parentRefs`) | the operator's own Gateway API gateway |
| `secret-store` | `secrets.yaml` (`secretStoreRef`'s `name`) | the operator's own `ClusterSecretStore` |
| `ghcr.io/scramb/memory-manager:0.0.0` | `kustomization.yaml` (`images`) | a released image tag |

`scripts/check-deploy-placeholders.sh` (run in CI, see below) fails the build if a real hostname
or a non-loopback IPv4 address ever lands in `deploy/` instead of one of these.

An operator applies this base through their own Flux `Kustomization` (or `kubectl apply -k`
directly) with a `targetNamespace` and a set of patches, not by editing it in place - see
"Operator overlay" below. `charts/` (a Helm chart, #45) and a worked Flux example repo (#46) are
separate, later work; this base works with either on its own already.

## What is *not* here

- The namespace itself, and any network policy restricting who may reach the pod - an operator's
  own cluster topology, not this project's to decide.
- `charts/` (Helm) and a full Flux `GitRepository`/`Kustomization` example repo - #45/#46.
- Cloudflare/tunnel-specific exposure notes - #47.
- Backups for the CNPG `Cluster` - it is a derived index (`memory-manager reindex --full`
  rebuilds it from the vault), not a primary store; an operator who wants point-in-time recovery
  anyway adds a CNPG `Backup`/`ScheduledBackup` and object-store configuration in their overlay.

## Required secrets

Every key below must exist in the operator's secret store, or the whole `ExternalSecret`'s sync
fails - not just the one key that is missing (`secrets.yaml`'s own comment). The `remoteRef`
`key`/`property` pairs in `secrets.yaml` (for example `memory-manager/vault-deploy-key` /
`private-key`) are illustrative paths; adapt them to how the operator's own store is laid out.

| Secret key | Purpose | How to generate |
|---|---|---|
| `SSH_PRIVATE_KEY` | the vault's deploy key | `ssh-keygen -t ed25519 -f deploy-key -N ''` - **not** read-only on the remote: the server pushes every write back |
| `SSH_KNOWN_HOSTS` | pins the vault remote's host key (`VAULT_SSH_KNOWN_HOSTS`) | `ssh-keyscan -t ed25519 git.example.com` (the real git host), reviewed against the host's own published fingerprint before trusting it |
| `VAULT_WEBHOOK_SECRET` | verifies the GitHub/Gitea push webhook's HMAC signature | `openssl rand -hex 32` |
| `OIDC_CLIENT_SECRET` | the upstream OIDC provider's client secret for `LOGIN_MODE=oidc` | issued by the provider when the client is registered there |
| `OAUTH_CLIENT_SECRET_KEY` | encrypts each DCR client's `client_secret` at rest (ADR-0004) | the one-liner in `src/memory_manager/auth/store.py`'s own `ValueError` message (generates a Fernet key) |

`LOGIN_MODE=password` (the quickstart alternative to OIDC, ADR-0004 L1) needs one more:
`ADMIN_PASSWORD_HASH`, generated with `memory-manager hash-password` (reads the password from
stdin) and added as its own key in the operator's overlay - not shipped in the base's
`secrets.yaml`, since a base configured for OIDC login has no provider for that key to come from.

## Environment

Set directly in `deployment.yaml` (placeholders, see the table above) or read from a `Secret`;
the rest keep the server's own defaults and need no operator action unless noted.

| Variable | Set where | Notes |
|---|---|---|
| `PUBLIC_URL` | `deployment.yaml` | must equal the `HTTPRoute`'s hostname, scheme included |
| `HOST`, `PORT` | image `ENV` (Dockerfile) | `0.0.0.0:8080`; not repeated in `deployment.yaml` |
| `DATABASE_URL` | `deployment.yaml`, from `memory-manager-db-app`'s `uri` key | generated by CloudNativePG, never written by hand |
| `VAULT_REMOTE`, `VAULT_BRANCH` | `deployment.yaml` | the vault's own git remote/branch |
| `VAULT_DIR` | image `ENV` | `/data/vault`; the `vault-data` `emptyDir` is mounted at `/data` - Git is the source of truth, this clone is rebuilt from `VAULT_REMOTE` on every pod start |
| `VAULT_SSH_KEY_FILE`, `VAULT_SSH_KNOWN_HOSTS` | `deployment.yaml` (paths into the `ssh` secret volume) | see "SSH runtime notes" below |
| `VAULT_WEBHOOK_SECRET` | `deployment.yaml`, from `memory-manager-secrets` | optional feature - the `/hooks/vault` route 404s without it |
| `LOGIN_MODE`, `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_ALLOWED_EMAILS` | `deployment.yaml` | `LOGIN_MODE=password` + `ADMIN_PASSWORD_HASH` is the alternative, see "Required secrets" |
| `OIDC_CLIENT_SECRET` | `deployment.yaml`, from `memory-manager-secrets` | |
| `LOGIN_NAMESPACES` | `deployment.yaml` | default namespaces for a subject with no `LOGIN_NAMESPACE_MAP` entry |
| `OAUTH_CLIENT_SECRET_KEY` | `deployment.yaml`, from `memory-manager-secrets` | |
| `LOG_FORMAT` | `deployment.yaml` | `json`; matches the image's own default, set explicitly for a log pipeline that expects it |
| `EMBEDDING_PROVIDER` and the other `EMBEDDING_*` | not set | defaults to `none` (full-text search only); add to the overlay to turn on Ollama/OpenAI-compatible embeddings |
| `METRICS_ENABLED` | not set | `/metrics` is on by default; set to `false` in an overlay patch to turn it off |

## SSH runtime notes

- **Known hosts.** Without `VAULT_SSH_KNOWN_HOSTS`, the server trusts whatever host key the
  remote presents on first contact (`StrictHostKeyChecking=accept-new`) - fine for a throwaway
  remote, not for a real deploy key. Setting it (as this base does, mounted from the
  `SSH_KNOWN_HOSTS` secret key) switches to `StrictHostKeyChecking=yes` against the pinned file
  instead; **recommended for every production deployment**.
- **Secret-mounted key permissions.** A Kubernetes `Secret` volume mounts its keys root-owned
  under the pod's `fsGroup`, which `ssh` refuses outright ("UNPROTECTED PRIVATE KEY FILE") -
  it checks the file's own mode bit-for-bit (0600/0400), not who can actually read it. The server
  works around this itself: if `VAULT_SSH_KEY_FILE`'s mode is not already safe, it copies the key
  once, at first use, into a private 0600 temp file and uses that instead
  (`src/memory_manager/vault/repo.py`). Nothing to configure for this; it is why `deployment.yaml`
  does not set a `defaultMode` on the `ssh` volume.

## Operator overlay (Flux example)

A Flux `Kustomization` pointing at this repo's `deploy/`, applying it into the operator's own
namespace with their own values patched in:

```yaml
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: memory-manager
spec:
  interval: 5m
  url: https://github.com/scramb/memory-manager
  ref:
    branch: main
  ignore: |
    /*
    !/deploy
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: memory-manager
spec:
  interval: 5m
  sourceRef:
    kind: GitRepository
    name: memory-manager
  path: ./deploy
  prune: true
  targetNamespace: memory-manager
  patches:
    - target:
        kind: Deployment
        name: memory-manager
      patch: |
        - op: replace
          path: /spec/template/spec/containers/0/env/0/value
          value: https://memory.example.com
    - target:
        kind: HTTPRoute
        name: memory-manager
      patch: |
        - op: replace
          path: /spec/hostnames/0
          value: memory.example.com
        - op: replace
          path: /spec/parentRefs/0/name
          value: my-real-gateway
        - op: replace
          path: /spec/parentRefs/0/namespace
          value: istio-ingress
    - target:
        kind: ExternalSecret
        name: memory-manager-secrets
      patch: |
        - op: replace
          path: /spec/secretStoreRef/name
          value: my-real-secret-store
  images:
    - name: ghcr.io/scramb/memory-manager
      newTag: "0.3.0"
```

Patching by JSON-pointer index (`/env/0/value`) is brittle across upstream reorders; an operator
who wants named-field patches instead can use a Kustomize `patches:` entry with a `target`
(`kind`/`name`) and a strategic-merge `env: [{name: PUBLIC_URL, value: ...}]` snippet in their own
`kustomization.yaml` just as well - both work, pick whichever is easier to keep in sync with this
base's changes.

## Rollout: bump the tag

1. Cut a release of this repo (the `Release` workflow builds
   `ghcr.io/scramb/memory-manager:X.Y.Z`); wait until it is green.
2. Bump `newTag` in the operator's own overlay (never `latest` - otherwise Git stops being what
   actually runs).
3. Check the render offline, and with a cluster context the diff:

   ```sh
   kubectl kustomize deploy/ >/dev/null
   kubectl diff -k path/to/operator-overlay/
   ```

4. Commit and push; Flux reconciles on its own interval, or immediately:

   ```sh
   flux reconcile kustomization memory-manager -n memory-manager --with-source
   ```

The schema migrates forward on its own at start (`db/migrate.py`); a release that needs a manual
step says so in its own release notes.

## Webhook setup (GitHub/Gitea)

Once `VAULT_WEBHOOK_SECRET` is set, `POST https://<PUBLIC_URL>/hooks/vault` triggers an immediate
sync instead of waiting for the next `VAULT_POLL_SECONDS` poll:

- **GitHub**: repository Settings → Webhooks → Add webhook. Payload URL as above, content type
  `application/json`, secret = the same value as `VAULT_WEBHOOK_SECRET`, event: "Just the push
  event".
- **Gitea**: repository Settings → Webhooks → Add Webhook → Gitea. Same URL and secret, trigger
  on "Push".

Either way the webhook body is capped at 1 MiB and rejected (401) without a valid
`X-Hub-Signature-256` (GitHub) or `X-Gitea-Signature` (Gitea) header.
