# ADR-0017 — API compatibility: SemVer over a tiered public surface, deprecation until next major

Status: Accepted · Date: 2026-10-11
Relates to: mcp, cli, deploy, docs, F-02 Client Integrations (WP-59); [ADR-0010](./0010-client-compatibility-profiles.md), [ADR-0005](./0005-note-format.md)

## Context

M17 brings memory-manager toward a 1.0 release shared by claude.ai, Claude Code and roughly a dozen other MCP clients plus operators running the Helm chart. None of them has ever seen a stable release before: tool parameters, error shapes, config env vars, the note format and CLI flags have all changed freely across 0.x. Once 1.0.0 ships, every one of those clients needs to know what changes without warning (a patch release) and what does not change without notice first (a minor or major release). `docs/compatibility.md` is the user-facing promise; this ADR is the decision behind it.

Three questions needed an answer before that document could be written:

1. **Scope.** Which parts of the server are "the API" at all? The MCP tool contract is the obvious one, but config env vars, the note format, CLI flags, Helm values and even metric names are all things an operator's automation can depend on.
2. **Deprecation period.** How long does a deprecated surface keep working before it can be removed, and in which release is removal allowed?
3. **Announcement.** Where does a deprecation show up, beyond a line in `docs/compatibility.md`?

## Options

### Scope

#### A — Narrow: tools, config, note format, CLI only
Pro: smallest surface to hold stable, matches issue #199's original wording exactly · Con: leaves out things operators clearly already automate against (Helm `values.schema.json`, HTTP paths, exit codes), so a "stable" release could still break their pipelines without warning.

#### B — Broad: the four above plus metrics, dashboards, audit-export fields and log format
Pro: nothing operators depend on is left unprotected · Con: metric names and log lines change for debugging and operational reasons far more often than an API should; holding them to a SemVer+deprecation bar would freeze normal operational work for no benefit to a client integration.

#### C — Three tiers: Stable (SemVer + deprecation), Operational (announced in release notes, no deprecation period), Internal (no promise)
Pro: separates "a client or automation calls this directly" (Stable) from "this is useful to read but not a contract" (Operational) from "implementation detail" (Internal), so each gets the right amount of ceremony · Con: three categories to maintain and classify new surface into, instead of one.

### Deprecation period

#### A — Removal in a later minor, one minor release plus 90 days after deprecation
Pro: shortest wait for operators who want old surface gone · Con: a "minor" release becoming breaking (even on a schedule) undermines the one promise SemVer exists to make — that a minor is always safe to take.

#### B — Removal in a later minor, two minors plus 180 days after deprecation
Pro: more notice than A · Con: still breaks the same SemVer promise; doubling the wait does not fix what makes A wrong in the first place.

#### C — Removal only in the next major, which must ship at least one minor release and 90 days after the deprecation was released
Pro: a minor is always a safe upgrade, full stop — the one property every tool downstream (Dependabot, auto-upgrading Helm releases, `uv lock --upgrade`) relies on; 90 days gives self-hosters one deploy cycle to notice a deprecation warning before it can disappear · Con: a deprecated surface can live for a long time if no major is due; that is the cost of the guarantee, not a flaw in it.

### Announcement

#### A — `docs/compatibility.md` only
Pro: one place to check · Con: nobody re-reads a markdown file on every upgrade; a deprecation that only lives there is easy to miss until removal.

#### B — A + GitHub release notes + runtime signals (tool description prefix, one server log warning per process, CLI stderr warning, startup warning for a deprecated env var)
Pro: shows up where the owner and operators already look (release notes) and where a client or script actually hits the surface (the running server, the CLI output) · Con: runtime signals are implementation work beyond this ADR and this task; they are promised here but built separately.

#### C — B plus a `CHANGELOG.md` "Deprecated" section via a new Conventional Commit type
Pro: deprecations would show up in the generated changelog automatically · Con: `CHANGELOG.md` is generated by release-please from existing Conventional Commit types (CLAUDE.md); adding a new type changes how every future commit is classified and is release tooling surface, not a documentation decision — out of scope here and not needed when the release notes already carry it.

## Decision

**Scope C, deprecation period C, announcement B.** Accepted by the owner on 2026-10-11.

- **Stable** (SemVer + deprecation): MCP tool names, parameters, result fields and annotations; structured error kinds; the `memory_guide` prompt name; compatibility profile names and how a profile is selected (`?profile=`, `MM-Client-Profile`, `serve --stdio --profile`); OAuth scopes `memory:read`/`memory:write`; HTTP paths including the OAuth/PRM metadata endpoints and `/hooks/vault`; config env vars with their defaults and config file formats (the `BLOCKLIST_FILE` TOML schema, `ERASURE_LOG_REPLAY_FILE`, `LOGIN_NAMESPACE_MAP`); the note format, its paths and `export` output; CLI commands and flags; the distinction between exit code `0` and non-zero (not the specific non-zero values, which are inconsistent today); `doctor --client --json` field names; Helm values (`values.schema.json`); image and chart tags.
- **Operational** (announced in release notes, no deprecation period): `mm_*` metric names and labels, dashboards and alerts, audit-export fields, log format, the `/account` HTML, human-readable CLI output.
- **Internal** (no promise at all): the Postgres schema and its migrations, the Python API, instruction/tool-description wording, error message text, token string formats, the Kustomize base's internals.
- A Stable surface may only be removed in the next major, and only once at least one minor release has shipped it as deprecated **and** 90 days have passed since that deprecation was released — whichever is later.
- **Security exception:** a security fix may break a Stable surface in a minor or even a patch release, announced in the release notes and, where applicable, a security advisory. This is the one case where SemVer's own promise yields to not shipping a known vulnerability.
- **Announcement** is the Deprecations register in `docs/compatibility.md` (the authoritative list of what is currently deprecated and when it may go), plus the GitHub release notes for the release that introduces the deprecation, plus four runtime signals: a tool description prefixed `Deprecated:`, one server log warning per process for a deprecated surface actually used, a CLI stderr warning, and a startup warning for a deprecated env var. The runtime signals are promised in `docs/compatibility.md`; implementing them is a separate task (not #199).

## Consequences

- `docs/compatibility.md` becomes the one place a client integrator or operator checks before relying on something or before upgrading; it must stay current whenever a Stable surface changes.
- Adding a tool parameter, env var, result field, error kind or enum value is additive and ships in a minor. Removing or renaming one, narrowing its allowed values, or changing a default needs a deprecation cycle first (or a major, immediately, for anything not yet deprecated).
- The Operational tier keeps metrics, dashboards and log format free to change for debugging and operational needs without going through a deprecation cycle — they still get a release-notes mention so operators are not surprised.
- The runtime deprecation signals promised here (tool description prefix, log warning, CLI warning, env var warning) do not exist yet; a deprecation announced before they ship relies on the register and release notes alone.
- Classifying genuinely new surface into the right tier is a judgement call at review time; this ADR gives the boundary, not an exhaustive list for all time.

### Addendum 2026-10-11 (#315)

A tool result carries two channels, and only one of them is Stable. `structuredContent` always matches the tool's `outputSchema` and is the Stable result contract already covered by "MCP tools" above. The text `content` channel is the MCP SDK's own rendering of `structuredContent`, not a second contract — it splits a list result into one `TextContent` block per element (`mcp/server/mcpserver/utilities/func_metadata.py:644-650` in MCP SDK 2.3.0), so `memory_read` returns a bare JSON object for one note but several blocks for several, while `memory_search` and the write tools always render one block. That inconsistency is exactly why the text channel is Operational, not Stable: clients should read `structuredContent` and tolerate the text rendering changing shape. Docs only, owner decision on #315; no code change.

## Reversibility

Cheap to tighten (moving something from Operational to Stable, or shortening nothing — the deprecation period can only ever be loosened for already-deprecated surface, not shortened, without breaking a promise already made). Expensive to loosen: reclassifying a Stable surface as Operational, or shortening the deprecation period, breaks the promise this ADR makes to everyone who already relied on it, and would need its own ADR with its own announcement.
